# Implementation Plan: Campaigns Management

- **Feature ID**: campaigns
- **FDS Version**: 1.0.0
- **Source Specs**: `features/campaigns/fds.md`, `features/campaigns/behavior.md`, `features/campaigns/visuals/figma.md`
- **Scenario**: C — New Feature with Cross-Feature Dependency (depends on `contacts` v1.0.0 and `groups` v1.0.0, per FDS frontmatter and `features/index.json`)

---

## 1. Phase 1 — Feature Foundation Refactoring (`groups`)

Campaigns must resolve live recipient contacts for a set of target groups, and validate that supplied `targetGroupIds` exist, without duplicating persistence logic in a new repository (Architecture §"Repository Layer", §"Forbidden Practices"). `ContactRepository.findByIds` (added for Groups' own Phase 1) is already sufficient to hydrate resolved recipient contacts, so **no change to `contacts` is required**. `GroupRepository` currently only exposes single-id lookup (`findById`) and per-group membership (`findContactIds`), neither of which supports batch group-existence validation or multi-group membership resolution, so two minimal, non-breaking extensions are added.

| #    | Task                                                                                                                                                                                                                                                                                        | Spec Reference                                                    |
| :--- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------- |
| P1-1 | Add `GroupRepository.findByIds(ids: string[]): Promise<GroupRow[]>`, returning only rows that exist and silently ignoring unknown ids (mirrors `ContactRepository.findByIds`).                                                                                                              | Campaigns FDS §5 (REQ-CMP-01), §8 (API Specification)             |
| P1-2 | Add `GroupRepository.findContactIdsForGroups(groupIds: string[]): Promise<string[]>`, returning raw (possibly duplicate across groups) contact ids for the given groups; deduplication is a Service-layer concern (Architecture §"Repository Layer" — no business rules in the repository). | Campaigns FDS §5 (REQ-CMP-03)                                     |
| P1-3 | Update the in-memory `GroupRepository` fake used in `backend/src/groups/group-service.test.ts` to implement both new methods, so existing Group unit tests keep passing.                                                                                                                    | Regression safeguard for Groups FDS (no behavior change intended) |
| P1-4 | Add unit tests asserting `findByIds` excludes unknown ids and `findContactIdsForGroups` returns the union (with duplicates left for the caller to dedupe) across multiple groups, with no change to existing `GroupRepository` methods' behavior.                                           | Regression safeguard for Groups FDS (no behavior change intended) |

This phase touches only `backend/src/groups/` (repository + its test double). No change to the `Group` data model, the `groups` ts-rest contract, or any Groups frontend/UI code.

## 3. Ambiguity & Conflict Report

None blocking. Several implementation clarifications are recorded (not ambiguities requiring a stop), each resolved without inventing unstated business rules:

1. **Scheduling trigger mechanism**: FDS §5 (REQ-CMP-05) requires processing to "start automatically when scheduled time is reached," but neither `rules/tech-stack.md` nor the existing codebase has an approved job/queue library, and the backend is a single long-running Express process. Resolved as an in-process interval poller (`CampaignScheduler`, native `setInterval`) — no new library, consistent with "No new libraries without explicit approval."
2. **Email delivery dependency**: `@aws-sdk/client-ses` is not currently installed. `rules/tech-stack.md` already lists "Amazon SES" as the approved Email technology, so adding its official SDK is treated as implementing an already-approved capability, not an unapproved new library category.
3. **Sender environment variable name**: FDS §6 gives two examples (`SES_FROM_EMAIL` or `SENDER_EMAIL`). `SES_FROM_EMAIL` is chosen as canonical (listed first in the FDS text).
4. **`targetGroupIds` persistence**: stored via a `campaign_target_groups` join table and computed at read time, mirroring the Groups feature's `contactCount`/membership precedent (`features/groups/plan.md` §3), rather than a JSON array column — consistent with `rules/architecture.md` and avoids a redundant field that could drift from actual associations.
5. **`Cancelled` status is reachable-in-schema-only for v1.0.0**: FDS §4 declares `Cancelled` as a legal `status` value, and REQ-CMP-07 treats it as immutable alongside `Sent`/`Sending`, but no functional requirement, behavior-spec flow, or §8 API method defines how a campaign ever transitions into `Cancelled`. This does not block implementing any stated requirement, so it is modeled in the schema/enum for FDS §4 fidelity but has no v1.0.0 code path that produces it. If cancellation becomes an in-scope requirement, that needs a new FDS version per `rules/workflow.md` §4 (Extension).
6. **Status tabs vs. full status enum**: `behavior.md` names only four tabs (`All`/`Drafts`/`Scheduled`/`Sent`). `Sending`/`Failed`/`Cancelled` campaigns are not hidden from the UI — they remain visible under `All` and via search, since no dedicated tab is specified for them.
7. **Send Now recipient-count preview**: `behavior.md` requires the Send Now confirmation dialog to display a "resolved recipient count," but FDS §4 has no such field and §8 has no preview endpoint. Resolved by computing it client-side as the deduplicated union of `contactIds` across the campaign's `targetGroupIds`, reusing the already-existing `GET /groups` endpoint (which already returns per-group `contactIds` as of the Groups feature's Integration Build Mode) — no new backend endpoint required. This is a preview only; the backend independently re-resolves live membership at actual send/schedule-due time per REQ-CMP-03, so a brief race window between preview and confirm is accepted, consistent with "live" resolution semantics.
8. **Duplicate Campaign's `name` field**: REQ-CMP-06 lists only Subject/Body/Target Groups as copied, silent on `name`. Since `name` is required but has no uniqueness constraint (unlike Groups), the duplicate copies the source campaign's `name` as-is; the user may rename it like any other Draft field.
9. **Editor route vs. modal**: Figma shows Campaign List (node `22:65`) and Create Campaign (node `25:65`) as separate frames, suggesting a dedicated page rather than Groups' single-modal pattern. Planned as `frontend/src/app/campaigns/new` and `/campaigns/[id]` routes. Frontend Build Mode must confirm this against the actual pulled Figma content — as happened for Groups, where the real Figma content contradicted the FDS's implied structure only once pulled during Build Mode, not during Plan Mode.
10. **Date/time picker**: no calendar/date-picker library is installed and `rules/tech-stack.md` doesn't list one. Planned as a native `<input type="datetime-local">` inside the existing `Dialog` component, requiring no new dependency.
11. **Partial-send-failure semantics**: FDS doesn't define per-recipient failure granularity. Planned as: dispatch is attempted for every resolved recipient; the campaign is marked `Sent` only if zero dispatch errors occurred, otherwise `Failed`.

No conflicts found between the FDS, behavior spec, visual reference, and `rules/architecture.md`, `rules/conventions.md`, or `rules/tech-stack.md`.
